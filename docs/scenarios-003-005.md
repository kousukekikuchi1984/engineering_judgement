# 3つの障害で、介入後の判断変更を試す

#001のN+1に、transaction競合、schema互換性、retry増幅を追加した。いずれもMid-level Backend Engineerを主な対象とし、15〜25分の試遊を想定する。所要時間と学習効果は未検証。初動では症状を提示し、原因の正解を入力する設問は置かない。

各YAMLの `design` に学習目的、因果、観測、誤読しやすい信号、副作用、影響、終了条件、採点根拠、5種類の代表経路、10項目の批判的レビューを定義した。行動の時間・費用・危険は同じファイルの `actions`、状態遷移は `effects / metrics / events` が正本となる。以下は因果と設計判断の読み解き用で、数値はすべて教材用の仮定である。

## #003：注文の一部が失敗し、再試行が増えている

[定義](../scenarios/003.yaml)。deployment後、注文の3%が失敗し、P99は3.2秒。DB CPUは38%で、単純な計算資源不足にも一時的な失敗にも見える。

隠れた原因は、通常注文と一括予約がorderとinventoryを逆順にlockすること。相互待ちでtransactionがabortされる。調査を選ぶと、使用率、40P01の失敗サンプル、lockの取得順、変更範囲、業務上許容できる停止範囲が別々に得られる。エラー名だけでは、何を止めるかや再試行の条件までは決まらない。

再試行を増やすと直後は失敗率0.7%、P99 1.5秒に改善するが、3分後は失敗率8%、P99 6.8秒へ悪化する。取得順を直さずに同時実行を増やした結果として扱う。直列化なら通常注文は安定するが、一括予約の待ち時間と低頻度のdeadlockは残る。一括予約の停止なら通常注文を回復できる一方、機能停止時間が積算される。rollbackと検証済み修正も選べる。

失敗試行を600注文/分で積算し、P99<2秒かつ失敗率<1%が丸3分続けば安定とする。制限は30分。停止を伴う軽減でも復旧宣言を許し、AARで原因残存と業務上の代償を示す。

採点では、限定停止は変更範囲と顧客影響、原因修正はlockの証拠と修正内容を根拠にする。abortと冪等性を確認しての短期retry軽減には合理性を認める一方、競合順序が観測済みなら無制御のretry増加の安全性を抑える。

代表経路は、証拠を集めて限定停止、競合を確認して修正、retryによる一時改善と悪化、根拠なしのrollbackによる偶然成功、lock調査を繰り返して時間切れ。これらをテストで実行する。

**批判的レビューでの修正：** 直列化で全deadlockが消えるモデルを避け、1件/分を残した。修正後に開始時のログを読む場合は保存サンプルだと明示した。再試行の安全性を議論できるよう、全transactionのrollback完了と注文IDの冪等キーを観測に含めた。一括予約の待ち件数・期限はまだ積算していない。

lockを一貫した順番で取得する方針は[PostgreSQLのExplicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html)を参照した。具体的な失敗率や3分という時間はこの資料から導いたものではない。

## #004：リリース後、一部のプロフィール取得だけ500になる

[定義](../scenarios/004.yaml)。旧版20%・新版80%が共存し、プロフィール取得の一部が500になる。全体CPUとDB CPUは低い。

原因はdisplay_nameをpublic_nameへrenameしたmigrationの先行。旧版は旧列を参照して失敗する。version別の観測で失敗の偏り、schema調査で契約の不整合、新版probeで動作と容量が分かる。

アプリだけrollbackすると旧版100%になり、取得が全件失敗する。旧版をroutingから外せば一旦改善するが、3分後に残る新版taskが過負荷となる。検証・増設して新版への移行を完了する経路と、互換viewを適用して両版を動かす経路がある。前者は追加費用、後者は作業時間と適用時の短いschema lockが代償になる。

300取得試行/分で影響を積算し、P99<1秒かつ失敗率<1%が丸3分続けば安定、30分で打ち切る。互換viewの適用分には失敗率4%以上を積算する。前進で回復しても旧版へのrollback可能性は戻らないため、AARに残す。

採点では前進にversion差と新版probe、互換対応にversion差とschemaの証拠が必要になる。同じrollbackでも、非互換を観測した状態では安全性を0に制限し、互換対応後なら適合する判断として扱う。原因名と行動名だけの固定採点にはしない。

代表経路は、検証して前進、両版互換を回復、旧版停止による一時改善と過負荷、根拠なしの前進、schema調査だけを繰り返して時間切れ。

**批判的レビューでの修正：** 削除したデータが元に戻るような操作を避けた。対象を読み取り専用APIに限定し、同じ基底値を旧名でも公開する互換viewとした。drain後に互換対応した場合は旧版へのroutingも戻す。書き込み・値変換・二重書き込みを含むmigrationには、このモデルをそのまま広げない。

段階的な互換変更の考え方は[Parallel Change](https://martinfowler.com/bliki/ParallelChange.html)を参照。実DBでのview実装やlock時間を検証したものではない。

## #005：配送見積もりAPIの遅延が、依存先の復旧後も続く

[定義](../scenarios/005.yaml)。外部APIの一時障害をきっかけに、こちらのtimeoutとretryが増える。外部障害は開始3分で収束するが、通常経路は回復しない。

3層が各最大3試行を行い、最大27回の呼び出しになりうる設定を置いた。即時retryと全体予算の欠如が、待ちと再試行の増幅を維持する。顧客400試行/分と外部呼び出し数の比較、同一traceの失敗、設定、分離した低頻度probeを調べられる。復旧通知だけで自分たちの経路も正常と判断すると、原因更新の機会を逃す。

worker増設は直後P99 2.2秒へ改善し、3分後は8秒・失敗率45%へ悪化する。受付遮断はP99 0.05秒になるが、取得は100%失敗する。総retry予算を制限すると3分かけて待ち行列を排出する。恒久的な単一層retryとjitterの修正、一時遮断して修正後に再開する経路もある。

400取得試行/分で影響を積算する。高速な受付拒否も失敗に含め、P99と失敗率の両方が健全で丸3分続くことを求める。予算制限は運用軽減、修正はretry方針への対応としてAARを分ける。

採点ではattemptsとconfigを根拠に制御を選び、遮断は顧客影響の確認も求める。設定を観測したのに予算なしで再開した場合は安全性を抑える。事業者の正常probeだけでは原因対応の根拠として扱わない。

代表経路は、増幅を確認して予算制限、遮断して方針修正後に再開、worker増設による一時改善と悪化、根拠なしの予算制限、trace調査だけを続けて時間切れ。

**批判的レビューでの修正：** 書き込みの重複副作用を省いたまま決済を扱うことを避け、read-onlyの配送見積もりにした。遮断中は遅延が低くても復旧にならない。待ち行列は3分の排出として簡略化しており、実queue長、各試行の確率分布、事業者の内部容量は再現していない。

retryを追加負荷として扱うこと、上限・backoff・jitterの考え方は[AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)を参照。現実のretry設計の正解を一つに固定する教材にはしない。

## 試遊で確かめる点

各シナリオに複数の復旧経路を置いたが、原因を覚えると調査を飛ばせる問題は残る。初見の参加者の判断記録を取り、再試行数と顧客試行の区別、互換性の確認、軽減と恒久対応の使い分け、悪化後の仮説変更を比較する。SeniorとMid-levelで差が出るという見立ては検証仮説であり、現段階で能力測定に使えるとは主張しない。

AARは実際の時刻、実行前に取得・引用した証拠、仮説・目的、介入直後と次の介入前の再観測を使う。規則の適合は自由記述の論理の正しさを保証しない。予測に反する結果をどう説明し、次の行動を変えたかは、timelineと本人の振り返りを人が読む。
