# 設計レビュー：条件付きで最小試作へ進む

判断記録と介入後の再観測を体験できる設計になったため、Phase 3へ進む。ただし「Engineering Judgmentを測定できる」「訓練により未知障害へ転移する」は未検証である。

| 観点 | 初期案の問題 | 修正と残る限界 |
|---|---|---|
| クイズ化 | 原因を当ててrollbackすれば終わる | 仮説・予測・根拠・確認条件を先に保存。復旧後の継続観測も必要。記録欄の埋め方を暗記する余地は残る |
| 原因既知の容易さ | 同じN+1を繰り返すと解法が既知になる | 初見プレイを主評価、再プレイは因果理解の練習とする。#001単独で未知問題への転移を主張しない |
| Senior/Midの差 | SQLの知識量だけで差が出る | 初期観測の選択理由、停止条件、軽減と原因対応の分離、悪化後の更新を人手で比較する。年次とスコアの対応は仮説 |
| 唯一路線 | trace→rollbackだけ高得点になる | changes＋初期影響を根拠にした早期rollback、DB＋flag停止、trace起点を許容。未調査rollbackを自動的に不合理とはしない |
| 挙動の整合性 | 固定流入でtaskだけ増えるとQPS増加は必然でない | 滞留・リトライ・per-task poolを前提に追加。N+1は個別slow SQLに必ず出るとは限らずquery頻度で観測 |
| 本番らしさ | 前日のdeployと急激な悪化に時間差がある | 通常ピークで大きなカートの処理が顕在化。rollback互換性は調査可能。数値は校正前の段階モデル |
| 採点の後知恵 | 最後に得た証拠で最初の行動を高評価する | 開始時の証拠スナップショットのみ参照。成功と記録品質を別表示 |
| 調査偏重 | 観測数を増やすと得点も増える | 介入時の引用の関連性を評価。時間中の顧客影響を毎分積算 |

## 試遊で判断すること

初見のMid-levelとSeniorを各3人程度募り、説明・プレイ・AARの実時間と操作の迷いを記録する。募集や送信は本実装に含めない。参加前にN+1経験とシナリオ既知かを確認し、結果の解釈に使う。

観察者は、画面のヒントなしで仮説を表現できるか、取得した証拠が次の行動に使われたか、一時改善後にDBを見直すか、反証を受けて方針を変えられるかを記録する。予測の不一致に対する自由記述を、参加者の役職を伏せて2人で読む。自動スコアは補助として並べ、採用・能力順位には使わない。

進行の目安は、参加者の過半数が支援なしで観測→判断→介入→再観測→AARを完了し、少なくとも複数の合理的な経路が現れること。これは試作を続けるための暫定基準で、学習効果の統計的検証ではない。自由記述が形式的、根拠を選ぶだけで満点、介入後の結果が読めない場合はUIとrubricを修正する。

将来の転移検証では、表面情報と原因構造を変えた未知D、事前/事後評価、比較群、盲検評価を用意する。#001の高得点や2回目の速さを転移の証拠にしない。
