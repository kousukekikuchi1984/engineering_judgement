# YAMLを追加すると、シナリオを選んで遊べる

`scenarios/` に1本の `.yaml` ファイルを追加すると、一覧、導入画面、指標、行動、観測結果、状態変化、AARに反映されます。シナリオIDごとのJavaScript分岐や登録リストはありません。

まず `002.yaml` を複製し、`id`、`title`、初期状態、行動、観測文を変更してください。#002は切り出しを確認するための短い比較デモです。20〜30分の教材として検証済みのシナリオではありません。

```sh
cp scenarios/002.yaml scenarios/example.yaml
# example.yaml の id を "example" に変更して内容を編集
npm run scenarios:check
npm test
```

サーバーはリクエストごとにYAMLを読みます。ファイルを編集したら、画面を再読み込みしてください。進行中のプレイは、開始時に読み込んだ定義を最後まで使います。編集した定義が途中で混ざることはありません。記録が必要なプレイは再読み込み前にJSONを保存してください。

## YAMLが決める内容と、共通部分を分ける

| 項目 | 定義する内容 |
|---|---|
| `schemaVersion / id / revision` | 書式のバージョン、一意なID、シナリオの改訂番号 |
| `title / audience / durationLabel / lead / description` | 一覧と導入画面の文章 |
| `initial / hypotheses / initialEvidence` | 隠れた初期状態、仮説の選択肢、初動の証拠 |
| `display` | 指標カードの項目・単位・補足、状態欄、グラフの指標・軸 |
| `metrics` | 状態と経過時間から求める観測値 |
| `healthy / limits` | 健全条件、安定確認に必要な分数、制限時間 |
| `actions` | 行動の表示名、所要時間、利用条件、効果、観測文、採点に使う証拠 |
| `events` | 時間経過で条件が成立した際の通知 |
| `costs / impact` | 費用、失敗試行数と機能停止時間の積算条件 |
| `scoring` | 証拠の有効期間、影響・費用の換算係数、未安定時の点数上限、予測対象 |
| `review` | 原因の開示、振り返りの問い、次に検討する対策 |

共通エンジンには「1分ずつ進める」「行動完了時に効果を適用する」「判断時点の証拠を保存する」「5軸の記録指標を計算する」という手続きを残しています。画面のレイアウトと採点の基本配点も共通です。YAMLが任意の画面構造や採点アルゴリズムを実行するわけではありません。

## 行動は条件と効果で定義する

以下は#002のscale-outに相当する、`actions` 内の1項目です。

```yaml
- id: scale
  label: ECSを8 tasksへ増設
  group: act
  duration: 2
  description: 4→8 tasks。費用 +4単位/分。DB接続への影響を観察する。
  available:
    eq: [{ref: state.tasks}, 4]
  effects:
    tasks: 8
  relevant: [app, db, impact, initial]
  feedback: CPUの飽和とDBの余裕を確認したうえで、増設後の結果も追ってください。
```

`group` は `observe`（観測）、`talk`（相談）、`act`（介入）のいずれかです。行動の所要時間は正の整数分です。`effects` に書けるのは `initial` で宣言済みの変数だけで、すべて行動完了直前の同じ状態から計算して一括適用します。

`relevant` は関連する証拠の取得元となる行動IDです。`initial` は初動の証拠を表します。互換性などの事前確認が必要な介入には `safetyEvidence: [changes]` のように書きます。結果確認になる観測には `verifies: true` を付けます。これらは構造化された記録の評価に使い、自由記述の意味を自動的に判定するものではありません。

## メトリクスと遅延効果も定義できる

#002のP99は次の条件式です。

```yaml
metrics:
  p99:
    if:
      - eq: [{ref: state.tasks}, 8]
      - 0.48
      - 3.1
```

#001では増設時に `scaledAt: {ref: state.time}` を保存します。その後の `metrics` から、`sub: [{ref: state.time}, {ref: state.scaledAt}]` で増設後の経過分を求めます。これが3以上なら接続逼迫時の値を返すため、一時改善と遅延悪化をYAMLで表せます。固定の時刻で行動を指定する一本道のスクリプトにはしていません。

使用できる式は、数値・真偽値・文字列・null、`ref`、および以下の演算子です。演算子の値は引数の配列になります。

| 演算子 | 意味 |
|---|---|
| `eq / lt / lte / gt / gte` | 一致、大小比較。引数2個 |
| `and / or / not` | 論理演算。`not` は引数1個 |
| `if` | 条件、成立時、不成立時の引数3個 |
| `add / sub / mul / div` | 四則演算。`sub / div` は引数2個 |
| `min / max / floor / round` | 最小・最大・切り捨て・丸め。`round` は値と小数桁数 |

`state.*` は初期変数と経過分 `state.time`、`metrics.*` はメトリクスの参照です。メトリクスは記述順に計算するため、別メトリクスを参照するときは先に定義します。循環参照や後方の未定義参照は読み込み時に拒否します。`healthy` は観測文などで使える健全条件の結果で、`metrics` の計算中には使えません。

JavaScript文字列、`eval`、外部処理の呼び出しはありません。新しい物理モデルや演算が必要なら、共通エンジンに処理とテストを追加します。確率的な障害、並行作業、任意のスクリプトは現時点の定義範囲に含めていません。

## 観測文は、観測した時点の値を差し込む

```yaml
observation:
  - when: {ref: healthy}
    text: P99 {{metrics.p99}}s。健全範囲に戻っています。継続時間を確認してください。
  - text: P99 {{metrics.p99}}s。まだ健全範囲に達していません。
```

上から最初に成立する文を使います。末尾には条件なしの文が必要です。取得した観測文と数値はその時点で保存し、後から更新しません。

`events` は毎分の更新前後で条件が不成立から成立へ変わった際に記録します。継続成立中は毎分同じ通知を出しません。行動の効果を適用した瞬間の通知用ではなく、経過時間による変化に使います。

## 実行順序とエラーの扱い

各分の開始時点の状態で費用・顧客影響を積算してから時刻を進めます。行動完了後に効果を適用し、観測文を生成します。制限時間へ達した分で終了し、未完了の行動効果は適用しません。健全条件が満たされてから丸々指定分数が経過すると安定と判定します。

`npm run scenarios:check` はYAML構文、必須項目、ID重複、所要時間、参照先、差し込み変数などを検査します。サーバーは起動前にも検査し、稼働後に不正なYAMLへ編集された場合は画面へファイル名とエラーを返します。入力形式の検査であり、本番らしい因果関係や、全経路が復旧できることを保証する検査ではありません。代表経路のテストと批判的レビューはシナリオ追加時にも必要です。

読み込みには[yamlパッケージの公式API](https://eemeli.org/yaml/)を使い、重複キーや不明なタグを拒否します。この定義形式ではアンカー・エイリアスを使いません。

JSON出力にはID、revision、YAMLのSHA-256、読み込んだ定義そのもの、判断記録を含めます。定義が改訂されても、そのプレイの条件を確認できます。初版から出力形式はversion 2へ変わりました。過去JSONを画面にインポートする機能はありません。

原因はプレイ中の画面に表示しませんが、現在の構成はローカル試作なので、APIの定義レスポンスやソースから確認できます。定義の分離は秘匿や不正対策の境界ではありません。


## 根拠に応じた判断評価と終了状態

#003〜#005には次の省略可能な項目を追加しています。#001〜#002の既存定義もそのまま動きます。

| 項目 | 動作 |
|---|---|
| `actions[].cost` | 実行開始時の一回分の追加費用。時間切れでも返還しない。省略時0 |
| `actions[].risk` | 行動カードに表示する代償・危険。採点条件とは別に記述 |
| `actions[].judgment` | 仮説・目的・引用した証拠・実行前の状態を照合する規則 |
| `actions[].hazards` | 実行前に取得済みの証拠と状態から、安全性の上限を決める規則 |
| `review.outcomes` | 終了時の状態に応じた説明。観測文と同じく最後は条件なし |
| `design` | 対象者、目的、因果、誤読しやすい信号、副作用、影響、終了条件、評価根拠、代表経路、批判的レビュー。プレイ画面には表示しない |

```yaml
judgment:
  - hypotheses: [schema]
    purposes: [mitigate, cause]
    evidence: [schema, versions]
    message: 両versionの契約を照合して互換性を回復しています。
hazards:
  - evidence: [schema]
    when: {not: [{ref: state.compatible}]}
    safetyCap: 0
    message: 互換性がない状態でアプリだけ戻すと失敗範囲が広がります。
```

`judgment` は配列内のいずれか1規則を満たせば適合とします。各規則の `hypotheses` と `purposes` はいずれか1つ、`evidence` は全件が必要です。証拠は `relevant` に含まれ、実行時に取得済み・有効期間内・引用済みでなければなりません。省略可能な `when` は実行前の状態で判定します。規則を定義した行動で適合を確認できなければ、Diagnostic Reasoningを最大4点に抑えます。規則に書かなかった合理的判断もありうるため、不適合は「誤答」と断定せず、人によるレビューを求めます。

`hazards` は引用の有無によらず、実行前に取得した有効期間内の証拠を使います。既知の危険を引用欄から外しても、安全性の上限を回避できません。複数成立したら最も低い上限が適用されます。後で得た証拠を使って過去の判断を評価し直すことはありません。

AARは実行時刻、選択した仮説、適合した規則、既知の危険、完了時と次の介入前の最後の再観測の数値を組み合わせます。自由記述を読んで評価する機能ではありません。保存済みログを読むだけの行動には `verifies: true` を付けず、現在の状態を確かめる観測に限定してください。

`design.paths` には `expert / alternative / dangerous / accidental / overInvestigation` を置き、それぞれ `actions` と `note` を定義します。行動IDの検査だけでは経路の成功を保証しないため、エンジンで実行するテストも追加してください。今回の数値は教材用の仮定であり、実測値ではありません。
